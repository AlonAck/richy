# Richy — QA audit & remediation plan

**Date:** 17 August 2026 · **Repo state:** `6498262` (master)
**Scope:** stuck screens, dead-end flows, wrong numbers, cheap-looking UI, plus legal / accessibility / store-metadata exposure.

---

## Context

Two months of complaints cluster on four themes: screens that get stuck, options
that can't be undone, numbers in the wrong place, and a look that reads cheap.
This audit walks the shipping code — `budget-app.jsx` (27,646 lines), `api/*`,
`sw.js`, `index.html`, and the legal pages.

Everything below is verified by reading the code, with `file:line`. Severity:
**P0** = user loses money or data, or is locked out · **P1** = visible breakage or
a flow with no way back · **P2** = polish and perception.

**One finding outranks everything else and explains a whole class of complaints:
after editing a debt, the app stops saving — silently, for the rest of the
session.** If customers have been reporting "it lost my data" or "my changes
disappeared", start there and read no further until it's fixed.

---

## The five to fix first

| # | Finding | Why first |
|---|---|---|
| 1 | **A1** — one debt edit kills all persistence, silently | Users lose an entire session of work with no warning |
| 2 | **A2** — `Activity.saveEdit` rebuilds transactions from scratch, dropping every flag | One long-press corrupts the opening balance permanently |
| 3 | **A3** — boot splash has no timeout or escape | "The app won't open", on the very first frame |
| 4 | **A4** — `_stockGet` poisons its in-flight map forever | Permanent spinner with no cancel and no retry |
| 5 | **C1** — Overview chart hardcoded to `$` | Wrong currency on the home screen; a one-line fix |

## A. Data loss and lock-outs (P0)

### A1 · Editing a debt writes `undefined` and silently kills every save
`budget-app.jsx:16360` — on **edit**, `form.id` is set, so `createdAt` is `undefined`:

```js
var rec = { id: form.id || …, name: …, balance: …, apr: …, minPayment: …,
            createdAt: form.id ? undefined : today };
var next = form.id ? debts.map(function(d) {
  return d.id === form.id ? Object.assign({}, d, rec) : d; }) : debts.concat([rec]);
```

`Object.assign` copies own enumerable keys **including undefined ones**, so it
overwrites the real `createdAt` with `undefined`. That object lands in
`blobRef.current` and goes to `CLOUD.saveUser` (`:2451-2453`), which calls
`.set(data)` with no `ignoreUndefinedProperties` anywhere in the repo (checked
`firebase-init.js`).

Firestore v8 rejects `undefined` field values by **throwing synchronously** — the
exception escapes `saveUser` *before a promise exists*. So the carefully-built
error handling in `flushSave` (`:26690-26706`) never runs:

```js
CLOUD.saveUser(accountKey, blobRef.current).then(function() { setSaveError(""); … })
  .catch(function(err) { … setSaveError(saveErrorMsg(err)); … });   // never reached
```

No banner. No retry. And `flushSave` is called from inside a `setTimeout`
(`:26679`), so the throw goes to the window handler and is swallowed entirely.

**The user edits one debt, then keeps working for an hour in a perfectly green UI
while nothing is written. Everything is lost on reload.**

**Fix:** ① `createdAt: form.id ? (existing.createdAt || today) : today`; ② strip
undefined in `saveUser` (`JSON.parse(JSON.stringify(data))` or a walk) so no
single field can ever do this again; ③ wrap the `flushSave` call site in
`try/catch` so a synchronous throw still raises the existing banner.

### A2 · `Activity.saveEdit` rebuilds transactions and drops every semantic flag
`budget-app.jsx:9110-9117`. The edit handler constructs `nt` from scratch rather
than merging, so `opening`, `trip`, `catchUp`, `transfer`, `bizExpense` and
`syncSource` are all discarded.

The opening-balance row is the worst case. It carries `catId: "opening"`
(`:15553`) — **and no category with that id exists** in `DEFAULT_CATEGORIES`
(`:249-260`, which runs c1–c6, c8–c11). So `catById` returns null and line 9110
falls through to `cats[0]` = *Housing*. From a single long-press and "Save
changes" **with no edits made**:

- `opening: true` is gone, so `isOpening()` (`:578`) is false
- the starting balance is now counted as **income earned this month** — savings
  rate and monthly income are wrecked
- `EditOpeningBalanceView` (`:15542`) can no longer find it, so saving there
  **prepends a second opening tx** (`:15558`) and the balance double-counts,
  permanently

Same mechanism silently injects catch-up rows into the real balance (`catchUp`
dropped, `:22954`) and breaks trip lump sums (`trip` dropped; and those rows use
`catId: "c7"`, `:11719`, which is **also** absent from `DEFAULT_CATEGORIES`).

**Fix:** make `saveEdit` merge — `Object.assign({}, t, { …editable fields })`.
That one change kills three findings. Then add the two missing categories, or
stop referencing them.

### A3 · The boot splash has no timeout and no escape
`budget-app.jsx:27402`:

```js
if (cloudReady() && !authChecked) { return <BootSplash />; }
```

`authChecked` is only set from the `onAuth` callback (`:26512-26549`). The success
path awaits `CLOUD.loadUser(cu.uid)` (`:26522`) → `.doc(uid).get()`. The `.catch`
at `:26546` covers **rejection**, not **non-settlement** — and a Firestore
long-poll stalled behind a captive portal or a cold cache simply never settles.
`authChecked` stays false and `BootSplash` (`:3260`) renders forever: a bare logo
and dots, no text, no retry, no timeout.

Force-quit is the only exit, and it reproduces on every relaunch until the
network recovers. This is the most likely source of "the app won't open".

`OnboardingScreen` already ships the right pattern at `:6371-6381` — an explicit
**"Continue without waiting"**. The boot gate needs the same: an ~8s fallback that
sets `authChecked` and renders "Can't reach your data" with *Retry* and *Sign
out*. Firestore's IndexedDB persistence means retry usually succeeds from cache.

Related, same file: `:26546`'s catch sets `authChecked` but never sets
`user`/`accountKey`, so `:27406` shows the **sign-in screen to somebody who is
signed in**. Signing in again re-enters the same failing path.

### A4 · `_stockGet` poisons its in-flight map permanently
`budget-app.jsx:710-746`. The de-dup map is cleaned only inside `.then`/`.catch`:

```js
714:  if (_stockInflight[key]) { _stockInflight[key].push(cb); return; }
715:  _stockInflight[key] = [cb];
725:      return fetch(stockApiUrl(params), { headers: headers });  // no signal, no timer
731/743:  var waiting = _stockInflight[key] || []; delete _stockInflight[key];
```

A fetch that never settles leaves the key in the map **for the life of the page**.
Every later caller pushes its callback onto a dead array and returns silently —
backing out and re-entering does not re-issue the request.

Downstream, each victim sets a flag that only clears in that callback:

- `:19206` `setSerBusy(true)` → chart spinner never clears
- `:20049` `gatherScoutData` — `need` is decremented only by the three callbacks,
  with **no overall deadline**
- `:20547` `StockScoutView.generate()` → `:20631` renders
  `<AIWorking expectedMs={30000}/>` **forever, with no cancel and no retry**. The
  auto-run effect (`:20565`) sets `genRef.current` before calling `generate()`, so
  it won't re-fire. The embedded instance (`:18399`) has no back button at all.

**Fix:** mirror `callClaude` — `AbortController` + 15s timer, and clear
`_stockInflight[key]` in a `finally`. Give `gatherScoutData` its own deadline so a
partial result still renders. Server-side, `api/stock.js:96` has no
`AbortController` and no `maxDuration` in `vercel.json`.

### A5 · Both crash screens are reload-only traps
`budget-app.jsx:2698-2712` (`ErrorBoundary`) and `index.html:78-85` each offer one
button: `location.reload()`.

The crashes a budget app actually gets are **data-shaped** — a malformed `tx`, a
`NaN`, a `catId` pointing at a deleted category. Reload re-loads the same document
and crashes again. On iOS there is no address bar behind it, so there is no manual
escape.

**Fix:** add *Sign out*, *Email support* (prefilled with the error), and *Export my
data* — reuse `exportData()` (`:24432`).

### A6 · Account deletion can report failure after succeeding
`api/delete-account.js` runs ~15 sequential awaits including an **un-timed
outbound fetch to the Leumi revoke endpoint** (`:108`), and `vercel.json` sets
`maxDuration` **only for `api/chat.js`**. On the default limit the function is
killed mid-flight. The client's `r.json().catch(…)` (`:24455`) then yields `{}`,
matching neither `ok` nor `partial`, so the user is told *"Deletion didn't go
through. Try again"* — even though `users/{uid}` was already deleted at `:88`.

On next load the auth listener (`:26521-26529`) sees `!data` and silently writes a
fresh `defaultBlob`. **The user believes deletion failed while their data is in
fact gone**, and now has a brand-new empty account.

Separately, when the server *does* report `partial`, the client shows a native
`alert()` (`:24462`) telling the user to email support, then signs them out
anyway — so they cannot retry. App Store 5.1.1(v) and GDPR art. 17 both expect
deletion to complete in-app.

**Fix:** add `maxDuration` for this route and an `AbortController` on the revoke
fetch; make the partial case retryable (keep the session, show what failed, offer
*Retry*); treat an empty/unparseable body as "unknown — check your account"
rather than "failed".

### A7 · Deleting a stock silently rewrites the account's cash balance
`budget-app.jsx:19320-19338` (`doDeleteStock`) filters the symbol's trades out.
But cash is *derived* from trades (`:1023`):

```js
(acct.trades || []).forEach(function(t) {
  cash += t.kind === "buy" ? -(t.cashAmount || 0) : (t.cashAmount || 0); });
```

So removing a symbol **refunds every buy and claws back every sell**. Buy $1,000
of AAPL, watch it grow to $1,500, delete → the $1,500 position vanishes and $1,000
reappears as cash, a net-worth drop of $500 from nowhere. With net sells on that
symbol, **cash goes negative**. The confirm copy (`:19726`) never mentions cash.

Compounding it, the single-trade delete confirmation (`:18765`) says
*"Your position math won't be recalculated"* — which is **backwards**;
`positionsOf` (`:1031`) and `investingCash` (`:1019`) are pure derivations, so it
absolutely is.

**Fix:** state the cash delta in the confirmation, or replace deletion with a
reversing entry. Correct the `:18765` copy either way.

## B. Dead ends — money and data you can't take back

### B1 · Bank Leumi DEMO writes fabricated transactions into the real ledger, permanently — P0
`budget-app.jsx:27073-27088` — connecting generates 4–7 invented transactions and
concatenates them into the user's actual `tx`, then saves. Every "Sync now"
(`:27097`) adds 1–3 more. These feed balance, budgets, category spend, savings
rate, streaks, XP, badges, net worth, and everything Richard is told.

1. **No way out.** Disconnect explicitly keeps them (`:24184` — "Transactions
   already synced stay in Richy"). No bulk removal; the only remedy is deleting
   them one at a time.
2. **They are invisible.** `syncDocToTx` tags them at `:8474`
   (`tx.syncSource = "leumi_finteka"`) and **nothing ever reads that field** — it
   appears exactly once in 27,646 lines. In Activity a demo row is
   indistinguishable from a real one.
3. **The export carries them**, unlabelled, as the user's official record.

The feature is honestly labelled DEMO on the way in (`:24148`). The problem is
entirely on the way out.

**Fix:** ① render a "Demo" chip wherever `syncSource` is set — the data is already
there; ② make **"Remove demo transactions"** the default action on disconnect;
③ mark or exclude them in `exportData`; ④ cap repeat syncs.

Related: the consent modal (`:24132-24152`) disables **both** exits while busy —
scrim `onClick` removed, Cancel `disabled`, no X — and nothing bounds
`props.onApprove()`. A hung connect leaves a sheet with zero exits. Its `.catch`
also calls `setBusy(false)` without `props.onClose()`, while the error text is
written to the view *behind* the modal, so the sheet just re-enables with no
explanation.

### B2 · "Sync your bank · Auto-import transactions" promises something that doesn't exist — P1
`budget-app.jsx:7204`, a quick-action on the Overview — the most-seen screen:

```js
{ id: "sync", icon: "refresh", title: "Sync your bank", sub: "Auto-import transactions", … }
```

There is no live bank connection for any bank. Behind the card: an iOS-only phone
automation plus a Leumi *demo*. The July study
(`reports/richy-sim-latest.html`) has this as the **top drop-off cause** — two of
the four simulated quitters name it, from both directions (an Israeli user not
with Leumi; a US user expecting Plaid):

> "the sync is for Bank Leumi and I'm not with Leumi, so I'm back to typing
> everything by hand … Prettier, more promising, same wall."

**Fix:** qualify before the tap — `sub: "iPhone auto-capture · Israeli banks"` — or
gate on platform/region. A promise that collapses one tap later costs more trust
than no card.

### B3 · Money added past a Budget Book's target is silently swallowed — P1
`budget-app.jsx:11157`:

```js
{ saved: Math.min(g.target, g.saved + n) }
```

Target 1,000, saved 900, add 500 → saved becomes 1,000; the 400 is gone with no
message. "Remove money" then subtracts the full typed amount (`:11123`), so
add-500-then-remove-500 leaves **500, not 900**. The round trip is not identity,
and the edit sheet (`:11094-11108`) exposes only name/target/deadline/link — the
user cannot correct `saved` directly.

### B4 · Deleting a savings pot silently zeroes every goal synced to it — P1
`:16649` removes the pot. Goals holding `linkType: "savings"` then get `null` from
`linkedAccountOf` (`:11005`) and `linkedBalanceOf` (`:11024`), so `:11197` falls
back to `g.saved` — which is **0** for a linked goal, because the Add/Remove
control is hidden while linked (`:11262`). The goal drops to 0% with no badge, no
warning, and a dead `linkId`. Same for `business:` and `investing:` links.

### B5 · Investing accounts can never be deleted or renamed — P1
`InvestingView` declares a delete-confirm state at `:17451` and **never uses it** —
the identifier appears nowhere else in the component. There is no rename either.
A typo'd or accidental investing account is permanent, occupying the Accounts hub
and the goal-sync dropdown (`:11059`) forever. Business accounts have close/delete
(`:21271`, `:21278`) but also no rename.

### B6 · Business "graduate" is one-way and wipes the roadmap — P1
`:20989-20994` sets `roadmap: null`, destroying **every completed milestone and
task checkmark**, then regenerates an empty one. Stage transitions are forward-only
(`:21336`, `var fwd = { idea: {…}, launching: {…}, running: {} }`), and `stage` is
editable only in the creation wizard (`:21943`).

Worse: **Richard can graduate the business autonomously** via
`@@BIZ[{"op":"stage",…}]` (`:21381`) with no user confirmation — an LLM reply can
irreversibly destroy the user's progress. That one deserves a confirmation gate
regardless of the rest.

### B7 · No way to undo a CSV import — P1
`:8835` — imported rows carry no batch id and no `imported` flag. Import 400 rows
with the wrong date format (the DD/MM toggle at `:8906`) or with "treat every row
as an expense" wrongly on (`:8912`), and the only remedy is **400 individual 500ms
long-presses**, each with a two-step confirm. A `resolveBulkDelete` helper exists
at `:629` but is not wired here.

### B8 · Only the last 6 entries of a savings pot or business account are reachable — P1
`:16717` and `:22064` both `.slice(0, 6)` with no "show all" and no pagination. A
wrong deposit made seven moves ago **can never be seen or deleted** — the only
escape is closing the whole pot. (The investing account's activity sheet at
`:17948` builds the full list correctly; copy that.)

### B9 · Trip reserve links break silently — P1
`reserveTrip` (`:11719`) stores `reserveTxId`. Deleting that tx from Activity
(`:9375`) leaves `trip.reserved: true` with a dead id: the UI still shows
"Reserved / Undo reserve" (`:12308`), and `syncTripTx` (`:11736`) becomes a silent
no-op. **From then on every trip expense the user logs stops affecting their
balance**, with no indication.

### B10 · Found Money dismissals and the recovered tally are write-only — P1
`:6860-6870`. Dismiss is permanent — `findings` filters on `dismissed` (`:6829`)
and `onSaveFoundMoney` is called from exactly one place; there is no un-dismiss,
no reset, no "show dismissed". A mis-tapped "Looks fine" (`:6995`, one tap, no
confirm) removes a real subscription leak from the audit forever. And `tally` only
goes up — a misclick on "I did it (+$X)" (`:7009`) permanently inflates the
headline and can permanently unlock a badge (`:2104`).

### B11 · Destructive actions with no confirmation at all — P1/P2
Single unconfirmed taps that destroy data: goal delete (`:11266`, sitting beside
"Edit" in a three-button row) and its twin at `:11109`; trip delete (`:12486`,
sitting directly below the benign "End trip"); business expense delete (`:22702`);
category delete (`:15006`, which also leaves ghost budget rows and dangling
`catId`s — unlike folder delete at `:14971`, which cleans up properly).

### B12 · Smaller sharp edges — P2
- **Silent clamping** — `:16604`, `:17677`: ask for 500 out of a 300 pot, get 300,
  no message.
- **Folder → "exclusive"** (`:10731`, `:10673`) silently deletes every category
  budget inside it; switching back does not restore them.
- **Transaction editing is a 500ms long-press** (`:9064`) with no pencil, no
  swipe, no visible affordance — the only way to fix a mistyped amount.
- **Trip and business entries can be deleted but never edited** (`:11753`,
  `:21198`).
- **`LogMonthView` is non-idempotent** (`:23005`) — "Add to my month" can be
  pressed repeatedly, creating duplicate sets.
- **Id collisions after a large import** — `:8782` reserves `Date.now()+i`, so a
  500-row import claims the next 500ms; a transaction logged in that window gets a
  colliding id and delete removes **both**.
- **StockScout overwrites the previous report** (`:20545`) — no history.
- **`EditOpeningBalanceView` Save does nothing on invalid input** (`:15550`) — no
  error, no navigation.
- **ScoutCinema leaves an invisible full-screen tap sink** (`:20405`) — the overlay
  fades to `opacity:0` with `fill: both` but keeps `position:fixed; inset:0;
  zIndex:500` and never sets `pointerEvents:"none"`. Unmount depends on
  `markIntroSeen` (`:20101`), which begins `if (!acct) return;`. Add
  `pointerEvents: closing ? "none" : "auto"`.

## C. Numbers in the wrong place

### C1 · The Overview trend chart is hardcoded to dollars — P1, one line
`budget-app.jsx:7566-7569`, used at `:7687-7688` for the chart's axis labels:

```js
if (a >= 1000) { var k = a / 1000; return sign + "$" + (k >= 10 ? Math.round(k) : k.toFixed(1)) + "k"; }
return sign + "$" + Math.round(a);
```

A shekel user sees **"$12.5k"** on the balance chart on the home screen. The
app-wide formatter `dollars()` (`:471`) is correctly currency-aware — this local
helper just bypasses it.

### C2 · Four settings rows are hardcoded to dollars — P1
`:24485-24488` — Monthly income, Monthly essentials, Savings, Total debt in
Profile → Privacy & data. These are exactly the numbers a user checks when they
suspect the app has their figures wrong.

### C3 · Richard is told the user's budgets in dollars — P1
`:13085` — `return c.name + " $" + sp + "/$" + b.limit;`. A shekel user gets an AI
advisor discussing their dollars — wrong numbers in the one place users are least
able to check them.

### C4 · Catch-up spending all lands on today — P1
`CatchUpScreen`, `:5842-5860`. Both the quick-total and per-category paths date
every generated row `today`, while the label reads "Spent earlier this
&lt;Month&gt;". A month of recalled spending becomes a single-day spike: the trend
chart shows a cliff, daily averages and "spent today" are wrong, and pace logic
reads one catastrophic day.

**Fix:** date to the period's midpoint (or spread), and flag `backfill: true` so
pace calculations can exclude them.

### C5 · Separators are always en-US — P2
`dollarsWhole` (`:484`) hardcodes `toLocaleString("en-US")`. Russian users expect
`1 234`, and several supported currencies group with `.`.

## D. Internationalisation — the store copy is not true

The App Store description (`APP_STORE_LISTING.md`) claims:

> "English, Hebrew, Arabic and Russian — with **full right-to-left layout**"

The translation table is healthy — 230 keys, complete in all four languages
(`:422-425`). The problem is how little of the app calls it: **388 `tr()` call
sites across 27,646 lines**, against ~281 hardcoded `label=`/`title=`/`sub=`/
`placeholder=` strings (versus 83 translated) and ~119 raw English text nodes.

| Screen | lines | `tr()` |
|---|---|---|
| AuthScreen + IntroCarousel | 5413–6263 | **0** |
| OnboardingScreen | 6263–6815 | **0** |
| CatchUpScreen | 5821–6016 | **0** |
| BusinessView | 20777–22921 | **0** |
| StockView | 19154–19816 | **0** |
| StockScoutView | 20501–20777 | **0** |
| PrivacyView | 24422–24550 | **0** |
| Profile | 25626–25902 | **0** |
| InvestingView | 17418–19154 | 18 |
| SavingsView | 16537–17187 | 53 |

**The entire signup and onboarding funnel is untranslated.** A Hebrew user's first
ten minutes are English text inside an RTL document — worse than plain English,
because mixed bidi throws punctuation and numerals to the wrong end of each line.

RTL support is direction-only. `applyLangDir` (`:411-419`) sets
`document.documentElement.dir`, and that is the whole mechanism. Against it:

- **0** logical CSS properties anywhere — no `marginInlineStart`,
  `paddingInlineStart`, `insetInlineStart`, `textAlign:"start"`
- **101** hardcoded physical alignments (`textAlign:"right"` ×33, `"left"` ×68) —
  in a finance app these are the amount columns
- **58** `left:` / **22** `right:` absolute positions
- **35** `translateX()` slides — forward/back animations play backwards
- **0** `row-reverse` handling

**Fix, staged:** ① the funnel first — it decides whether a non-English user ever
reaches the app; ② swap physical for logical properties, which fixes most layouts
mechanically; ③ mirror `translateX` under `dir="rtl"`; ④ **until ① and ② land,
soften the store copy** — drop "with full right-to-left layout". Metadata that
overstates is an Apple 2.3 risk and a consumer-protection risk, and it is a
one-field edit that needs no build.

Minor: `CatchUpScreen`'s `localeMap` (`:5832`) still lists `es/fr/de/pt`, retired
in August.

## E. Accessibility

| | count |
|---|---|
| `onClick` handlers | 466 |
| `role="button"` | **0** |
| `tabIndex` | **1** |
| `aria-label` | 17 |
| `fontSize` declarations | 1,654 |
| …under 12px | **419** |
| `rem` units | **0** |

- **No Dynamic Type.** Every size is hardcoded px. A user who enlarges text in iOS
  Settings sees no change. The July study already names "small text" as a
  complaint.
- **Keyboard and switch control** reach almost nothing; icon-only controls are
  unlabelled for VoiceOver.
- Reduced motion **is** handled well (`:2763`, `:2799`, `:2976`) — that part is done.

The EU Accessibility Act has been enforceable since June 2025 and consumer
financial apps are within its intended scope. Richy is a budgeting tool rather
than a regulated financial service, so scope is arguable — but the gap is large
enough to close on its own merits.

**Fix:** a `fs()` helper scaling the px scale off a root multiplier, plus a
text-size setting; add `role="button"` + `tabIndex={0}` + `onKeyDown` to the shared
primitives (`ProfileRow`, `InfoRow`, `Card`, `JrBtn`) — a handful of components
cover most of the 466 sites.

## F. Navigation, polish and privacy details

- **The back-layer stack knows about only two overlays** — `:27350-27353` handles
  `sheet` and `timeframeMenuOpen`. Invisible to it: `LeumiDemoConsentModal`,
  `BankSyncHelpChat`, `BankSyncJourney`, `ScoutCinema`, `ScoutBasicsStory`,
  Advisor's history, `BigDecisions`' overlay, the trip and business stories. On
  Android, Back therefore **pops the tab underneath** — the modal closes but the
  user is also thrown a level back. Escape on desktop (`:27388`) does nothing in
  any of them.
- **Onboarding screen 0 can brick a first run** — `:27358` swallows hardware Back
  during setup; the header renders no back chevron at `qIndex === 0` (`:6582`);
  and "Let's go" is gated on `greetDone` (`:6781`), set only from `TypeReveal`'s
  interval completing (`:3305`). Miss that callback and a brand-new user has a
  disabled button, no back, and a swallowed Back. Cheap hardening: a 6s
  `setTimeout` fallback alongside the reveal.
- **Trip/business story phases have no header at all** (`:11959`, `:21639`) — fixed
  full-screen with only a "next"; no back, no close until every beat is done.
  `BankSyncJourney` (`:23991`) does this correctly; copy it.
- **Dead back control** — `:11982` renders the trip-journey chevron unconditionally,
  so at `tq === 0` it is visible and does nothing.
- **Four native browser dialogs** — `:24184`, `:24295`, `:24441`, `:24462`. In the
  Capacitor shell these render as a system alert titled with the app's origin, on
  the two most consequential screens in the app. Replace with `Overlay` (`:4691`),
  which is already well built.
- **Reminder notifications leak amounts to the lock screen** — `:9598`, `:9614`
  produce "You owe ₪4,500 — Loan from Dad", visible to anyone glancing at the
  phone. Make the body generic, or add a "hide amounts in notifications" setting.
- **Type-`DELETE`-to-confirm is Latin-only** (`:24533`) — Hebrew, Arabic and Russian
  users must switch keyboards to delete their account.

## G. Carried over from the security review (still open)

`reports/security-review-2026-08-15.md` issue #5 — the client controls Richard's
system prompt — is **not fixed**, and the partial work is not wired up:

- `api/chat.js:85` still reads `var system = body.system || "";`
