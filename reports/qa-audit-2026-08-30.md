## 2. Genuinely new — both P0

### NEW-1 · Creating or joining a household wipes every budget, goal and category
`:3438` · `:32499-32505` · `:32605`

This is **not** the stale-closure bug from 25 Aug (§2.8a). It is a second, independent failure in the same seven lines, and it destroys more.

`createHousehold` writes a document with no `budgets` / `goals` / `categories` fields:

```js
var data = { name, createdBy, memberUids: [uid], members: [...], pendingEmails: [], createdAt };
```

The live subscription then unconditionally overwrites local state from that empty document:

```js
setBudgets(hh.budgets || []);       // → []
setGoals(hh.goals || []);           // → []
setCategories(hh.categories || []); // → []
```

`save()` (`:32605`) rebuilds the entire user blob from current state with no merge guard, so the **next save of any kind** — adding a transaction, changing the theme, dismissing a tip — persists `budgets: []`, `goals: []`, `categories: []` to Firestore. Wiping `categories` also orphans the `catId` on every historical transaction.

Trigger: one **"Accept & join"** or **"Create household"** tap. No warning. `onLeaveHousehold` restores nothing.

**Fix:** seed the household doc from the creator's data on create; merge on join; and refuse to persist an empty array over a non-empty one. That last guard alone would have caught this *and* the 25 Aug stale-closure bug.

### NEW-2 · The 26 Aug advice fix missed a second advice surface
`:20842` (`investPlanOrders`) · `:22736` (`investPlanFor`)

`90110af` and `b26496e` correctly closed Stock Scout and put `GUARDRAIL` (`api/_prompts.js:233`) in front of Richard. But the **investing allocation engine is deterministic client code** — it never passes through `api/chat.js`, so it never sees the guardrail.

It hardcodes named securities (VTI, QQQ, VXUS, BND, IBIT), fixes allocations per plan, selects the plan from the user's **risk-reaction questionnaire** (`investPlanFor(reaction, horizon)` — that is suitability profiling), and returns `{ symbol, pct, amount, price, shares }`: a named ticker, a cash amount, and a share count.

That is the exact thing the guardrail forbids and the exact thing `terms.html:49` says we don't do — *"not to suggest amounts to invest"* — while `terms.html:52` describes Investing as *"a tracker: it records holdings you already own."*

**This needs a decision from you, not a ticket.** Either strip the amounts and share counts and decouple plan selection from the questionnaire, or get licensed. The lesson for the process: the advice fix was scoped to the LLM path, so a non-LLM path producing the same output survived it. Any future guardrail needs to sit at the point financial strings are *rendered*, not at the API boundary.

## 4. What is genuinely solid

Stated plainly, because it narrows where to look and because the last two reports understated it:

- **No NaN or Infinity path exists.** I traced every division and every `* 100`. All guarded.
- **Float money is handled** — `round2()` (`:1362`) uses `Number.EPSILON`; `parseImportAmount` handles European decimals, thousands separators and parenthesised negatives.
- **One currency formatter**, 54-currency table with per-currency minor units. Exactly one literal `₪` in 2.2MB — the table row itself.
- **Client network layer is well hardened** — `callClaude` and `_stockGet` both have AbortController + settle-once guard + hard deadline. `api/chat.js` has its own 45s abort. Boot has an 8s fallback into `BootRetryScreen`.
- **Local AI fallbacks** mean an API failure degrades rather than dead-ends.
- **Privacy is strong** — `privacy.html` names Anthropic explicitly including image attachments; the six processors are listed; the four actual external hosts in `api/` are all disclosed. Amendment 13 and cross-border transfer both covered.
- **`api/delete-account.js` is well built** — uid from the verified token only, subcollections before parent, handle released, batches chunked at 400, returns `207 partial` rather than lying.
- **Rest of `firestore.rules` is tight** — `syncInbox` denies client writes, handles are create-only, `profileStats` is follower-gated, `list` denied to prevent scraping. `:60` is the one loose rule.

## 5. What I actually recommend

The bug list is not the problem. We have three of them. **The problem is that TIER 0 in `ROADMAP.md` has no mechanism behind it**, so it loses to whatever is more interesting that week. Two audits said "fix before building anything new"; the next commit was a 3,900-line feature.

**Do these four things, in this order:**

1. **Ship the four one-line fixes today.** `T.ink3` (693 contrast failures), the `apply5030 20` typo (Richard's buttons start working), `if (!r.ok)` before both `sw.js` `c.put()` calls (bricked-app-shell complaints stop), and the `firestore.rules:60` field pin. Together this is under an hour and it is the single best hour available to us.

2. **Add the guard, not the fix.** One assertion in `save()` — refuse to persist an empty `budgets`/`goals`/`categories` array over a non-empty one — closes NEW-1 *and* the 25 Aug stale-closure bug *and* the whole class. Same shape for a `.finally()` lint rule: 13 busy flags, zero `.finally`, and that is the documented root cause of "stuck screens."

3. **Add error telemetry.** The 25 Aug report called this out and it is still the reason complaints reach us as App Store reviews instead of as a worklist. We are auditing by reading 33,000 lines because we have no other signal. This is the highest-leverage item on the page and it is not a bug fix.

4. **Freeze features until TIER 0 is closed.** Not as a process opinion — as arithmetic. `CAMPAIGN_LAUNCH_2026-10.md` puts iOS launch on **5 October: 36 days away.** Waves 1 and 2 below are about nine days. There is room to do this properly, but only if nothing else gets built first.

### Nine-day plan

**Days 1–2 — stop the bleeding**
The four one-line fixes above. The `save()` empty-array guard. The functional-form fix for the stale closure.

**Days 3–7 — reversibility**
A 10-second **Undo** toast, implemented once and applied everywhere (keep the pre-delete array in a ref). This converts the entire "dead end" complaint class into a non-issue in one change, and it is strictly better than adding eight separate confirmation dialogs. Then: goal-overflow clipping, the stock-delete cash rewrite and its false confirm copy, the `onSaveFinancial` whole-key replace, and routing Richard's category/folder deletes through the red destructive card.

**Days 8–9 — stuck screens**
One `localToday()` / `localMonth()` helper replacing all 67 UTC sites (fixes the wrong-day and wrong-month bugs together). `.finally()` on all 13 busy flags. `.catch()` + the existing `saveError` banner on the sync-inbox write. AbortController on both `sendTest` copies.

**Before submission — legal and store**
Decide NEW-2. Then the accessibility sweep (`htmlFor`/`id` on 90 inputs, `aria-label` on 413 buttons, 44px on `JrIconBtn`) — this is an App Store Guideline 1.5 and Google Play accessibility concern, not just a quality one. Then translate the five untranslated screen groups: Investing, Business/CFO, Debts, Bank Sync and most of Profile still render raw English into an RTL document.

## 7. One note on method

The line numbers in the two previous reports no longer resolve, because the file grew by ~3,900 lines after they were written. That is a small thing that quietly makes old findings harder to action, and it compounds every time we ship a feature ahead of the fixes. Anchoring findings to code strings rather than line numbers — as this report does — costs nothing and survives.

The underlying reason all three audits took days of reading is that the app is **33,642 lines in one file**. "Is this pattern applied everywhere?" is currently unanswerable except by grep. That is worth fixing after launch, not before.
