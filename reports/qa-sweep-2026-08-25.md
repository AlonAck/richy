## 1 · Legal — the two items that outrank every bug

### 1.1 Stock Scout is unlicensed personalised investment advice (highest risk)

`budget-app.jsx:22034-22100`, `:22501` (`StockScoutView`)

The feature gathers a candidate pool of real securities, sends them to Opus, and
the system prompt says:

> "…hunting for the most promising opportunities for THIS person right now…
> Have a genuine view… Rank the 2 or 3 strongest ideas. **Size each suggestion
> to what they can actually afford: never more than their available cash**,
> smaller for a beginner or a nervous investor…"

Then a follow-up chatbot (`:22113`) continues the conversation with
`"they have <X> of investing cash and are <experience level>"` in its prompt.

Measured against חוק הסדרת העיסוק בייעוץ השקעות (תשנ"ה-1995) s.1 — advice on the
**כדאיות** of buying, holding or selling **ניירות ערך** — this is not near the
line, it is over it:

- specific named securities, not categories
- an explicit opinion on each ("have a genuine view")
- **sized to the user's actual cash balance and stated risk tolerance**

The media exemption normally relied on, s.3(a)(4), is conditioned by s.3(b) on
telling the user the advice is *not* tailored to their individual circumstances.
Stock Scout's entire selling point is that it is. The disclaimer in
`terms.html §3` does not carry this, because the exemption it would rely on has
its condition contradicted by the feature itself.

Exposure under s.57(a)(1): **two years' imprisonment or a fine, doubled for a
corporation.**

**Move:** turn Stock Scout off in production this week. It is the only feature in
the app with criminal exposure attached, it is not core to budgeting, and
switching it off is genuinely small — drop the `scout` entry from
`INVESTING_HUB_TABS` (`:28061`) and guard the `scout` tab route (`:29687`,
`onOpenScout`). Bring it back only as non-personalised education — no position
sizing, no cash-balance input, no per-security verdict — or behind a licence.

### 1.2 The guardrail can't be enforced anyway — clients set Richard's system prompt

`api/chat.js:85` — `var system = body.system || "";`

The system prompt arrives from the browser. Any signed-in user can post whatever
they like and get an unconstrained model on our Anthropic bill, with every
content boundary stripped. `api/_prompts.js` — the server-side registry added
specifically to fix this — **is never `require`d by `chat.js`**. It is dead code.

This means even if we write a perfect "never advise on a specific security"
rule, it lives on the client and is trivially removed. Both the legal boundary
and the spend limit are unenforceable until the registry is wired up. Flagged in
the 15 Aug security review, flagged again on 17 Aug, still open.

### 1.3 Terms and Privacy are English-only, for a Hebrew market

`terms.html:2` and `privacy.html:2` are both `<html lang="en">`, with no Hebrew
version — while `landing.html:2` is `<html lang="he" dir="rtl">` and the app
ships he/ar/ru. The in-app consent checkbox at signup links to these English
pages, and `PrivacyView` opens them (`budget-app.jsx:26517-26518`).

An Israeli consumer agreeing to English-only terms they were recruited to in

reads.

The content of both documents is genuinely good — this is a translation job, not
a rewrite.

### 2.0 "Redo Questionnaire" is a trap that survives force-quitting the app (P0, new)

`budget-app.jsx:29481` (`handleRetakePlan`), reachable from Profile → your plan →
the big orange **"Redo Questionnaire"** button at `:27018`.

```js
function handleRetakePlan() {
  setOnboardingDone(false);
  ...
  merged.onboardingDone = false;
  blobRef.current = merged;
  flushSave();          // <- persisted to Firestore
}
```

At `:29473`, `if (!onboardingDone) return <OnboardingScreen …/>` — and
`OnboardingScreen` is passed **no `onCancel` or `onBack`, and renders neither**.
So a curious user taps a button labelled "redo my questionnaire", lands on
question 1 of 10, and there is no way out. Because `flushSave()` writes
`onboardingDone:false` to the cloud, **force-quitting and reopening puts them
straight back at question 1.** Reinstalling doesn't help either.

The only exit is completing the whole funnel: 10 questions, then an un-skippable
6-beat animated "math story" (`:6841`, no back and no skip), then a commit
screen, then waiting on AI plan generation. Roughly five minutes, from a tap they
probably meant to explore.

**And finishing it wipes every budget they ever made.** `:29211`:

```js
if (suggestedBudgets && suggestedBudgets.length) {
  setBudgets(suggestedBudgets);        // full replacement
  merged.budgets = suggestedBudgets;
}
```

The primary CTA on the final screen (`:7198`, "Yes, set up my budgets") passes
`suggestedBudgets`, replacing the entire array — folder budgets, growth targets,
sub-limits, all of it. No warning, no confirm, no undo. Only the small grey
"I'll set them up myself" link (`:7199`) passes `null` and spares them.

This one flow explains a lot of "the app deleted my budgets" on its own.

**Fix:** an exit on `OnboardingScreen` when `onboardingDone` was previously true
(don't persist `false` until they actually finish), and merge rather than replace
suggested budgets — or at minimum confirm the overwrite by name.

### 2.6 The crash screen is an infinite loop, and we never hear about it (P0)

`budget-app.jsx:3384-3405` (`ErrorBoundary`) offers exactly one control:
**"Reload Richy"**. Nothing else — no sign out, no switch account, no export, no
"clear local state".

If the crash is caused by something *persisted* — one malformed transaction, a
`NaN` amount, a row from a half-finished import — then reload loads the same data
and crashes again. The user is in a loop they cannot exit from inside the app.
Their only escape is deleting the app, which does not help, because the bad row
is in Firestore.

`BootRetryScreen` (`:29468`) — added on 17 Aug for the boot-hang bug — gets this
right, with **Retry *and* Sign out**. The ErrorBoundary just needs the same
second button.

Worse: `componentDidCatch` (`:3387`) only calls `console.error`. I grepped the
whole tree — `index.html`, `budget-app.jsx`, `sw.js`, `firebase-init.js`, `api/` —
for Sentry, Bugsnag, Rollbar, LogRocket, Crashlytics, `window.onerror` and
`unhandledrejection`. **There is no error telemetry of any kind.**

So we have zero visibility into production failures. Every crash reaches us, if
at all, as a one-star review weeks later — which is a large part of why the last
two months have felt like they came out of nowhere. Wiring up any crash reporter
is roughly half a day and would convert "customers are complaining" into a
worklist.

And the crash it catches is usually **deterministic in persisted data**, which is
what makes the loop inescapable rather than merely annoying: `loadData`
(`:28385-28452`) guards for null with `|| []` but does **no type validation**. A
`trips` value stored as an object survives `data.trips || []` and then throws at
`props.trips.map` (`:12674`). Reload → same data → same throw.

One related trap worth fixing at the same time: `sha256Hex` (`:9628`)
dereferences `crypto.subtle`, which is `undefined` on any non-secure origin. It's
called synchronously from `onEnableBankSync` (`:29100`) inside an onClick — a
*synchronous* throw, which React error boundaries do not catch. `setBusy(true)`
has already run, so the button sticks at "Turning on…" with only a raw TypeError
in a console nobody is reading.

### 2.6a THE root cause of "stuck screens": offline Firestore writes never settle

This is the single most important technical finding in the report, because one
mechanism explains most of the "it just spins forever" complaints.

`firebase-init.js:44` enables offline persistence:

```js
firebase.firestore().enablePersistence({ synchronizeTabs: true }).catch(function () {});
```

That's a good feature. But it changes promise semantics: with persistence on,
`.set()` / `.update()` **apply locally immediately while the returned promise
only resolves on server acknowledgement.** Offline or on a stalled connection it
stays pending forever — so **neither `.then` nor `.catch` runs.**

Every busy flag in the app is cleared inside a `.then`/`.catch`. There are
**13** `setBusy(true)`-style calls and **zero `.finally()` in the entire file.**
So every one of these hangs permanently on a bad connection:

| Flow | Line | What the user sees |
|---|---|---|
| **Signup** | `:6218-6253` | Worst case. Auth succeeds (REST, works on a weak link), then `CLOUD.saveUser` (`:3145`, a `.set()`) hangs. The "Have an account?" link is hidden on this step (`:6514`) and there is no back button in `AuthScreen`. And `window.__cbSignup` stays `true`, which tells the auth listener to stand down **permanently** (`:28547`) — so even after a force-quit and sign-in, `user` is never set. **Result: an account in Firebase Auth with no Firestore doc, and a user who cannot get in.** |
| **Bank Sync enable** | `:26285`, `:29095` | "Turning on…" forever, `disabled={busy}` blocks retry. |
| **All of Collab** | `:16963` | Create / join / invite / leave household. "Joining…" forever — while the join has *already applied locally*. |
| **Handle claim** | `:27417` | Same. |
| **Every autosave** | `:28742` | Neither branch runs, so the "changes haven't saved" banner (`:28182`, which is well built) **never appears**, no retry is armed, and each further edit leaks another pending promise. Silent, unbounded. |

**This is why customers say the app freezes.** It isn't random — it's every
network-touching button, on every flaky connection.

**Fix:** for writes, don't await the server ack — Firestore already applied it
locally. Resolve the UI optimistically and use a separate connectivity signal for
the "not saved yet" banner. At minimum, add `.finally()` and a timeout to every
busy flag, and never gate a retry behind the flag that got stuck.

### 2.6b Six of eight `fetch` calls have no timeout

`callClaude` (`:12584`) and `_stockGet` (`:1409`) are genuinely well built — 55s
timer, `AbortController`, settle-once latch. They are also the **only two** of
eight `fetch` sites with any deadline.

Bank Sync's `sendTest` (`:25981` and again at `:26310`) has a `.catch`, so a
*failure* is handled — but a **hang** isn't, and mobile networks hang rather than
fail. The guard `if (testState === "sending") return` (`:25976`) then blocks
retry, so the last page of the 8-step phone-setup journey ends in a permanently
disabled "Sending…". Account deletion (`:26458`) is the same shape, on a GDPR
flow where the user can't tell whether their data was erased.

Server side, `api/stock.js:96` (`getJson`) has no `AbortController` and no
`maxDuration` entry in `vercel.json` — which lists only `api/chat.js`. Same in
`api/leumi-fintaka.js`, which runs on a daily cron.

**Fix:** extract `callClaude`'s pattern into one `fetchWithTimeout()` and route
all eight sites through it. Add `maxDuration` for `stock.js`, `bank-sync.js` and
`delete-account.js`.

### 2.6c Firestore listeners fail silently and permanently

Firestore does **not** auto-resubscribe after an `onSnapshot` error. Both
listeners in the app swallow it:

- **`subscribeSyncInbox` (`:3161-3171`)** — the error callback is
  `function() {}`, literally empty. On a token expiry or a rules blip the
  listener dies for good. The user taps Apple Pay, the transaction reaches
  Firestore fine, and it **never appears in Activity** — while Bank Sync still
  shows a green "connected" dot. Nothing anywhere says why.
- **`subscribeHousehold` (`:3234-3240`)** — the error callback does `cb(null)`,
  making "permission denied" indistinguishable from "the doc is gone". So when a
  partner removes you, the membership-check branch at `:28608` is never reached,
  `householdId` stays in your blob, and Collab silently falls back to the empty
  "create a household" state with no explanation.

### 2.6d The service worker can cache an error page as the app, permanently

`sw.js:88` (navigations) and `sw.js:103` (`/dist/app.js`) both write the response
into the cache **without checking `r.ok`** — unlike the generic branch at
`sw.js:116`, which does check. So a Vercel 502/503 HTML page gets stored as
`/index.html` *and* as `/dist/app.js`.

From then on, every offline launch serves that error page as the shell, and
`<script src="/dist/app.js">` receives a `text/html` body the browser refuses to

happens to overwrite it. `ignoreSearch: true` at `:105` means the poisoned bundle
entry matches every future `?v=` too.

*Real user:* opens Richy during a 30-second platform blip, closes it, gets on the
train, opens it again — white screen. Reinstalling is the only fix they'll find.

**Fix:** `if (r.ok)` before both `c.put()` calls. Two lines.

### 2.8a Couples mode silently deletes transactions (P0, new)

`budget-app.jsx:28621`, inside the household subscription:

The `useEffect` deps are `[householdId, accountKey]` (`:28624`), so this callback

## 3 · Numbers in the wrong place

### 3.1 The app runs on two different calendars (new — the big one)

There are two "what day is it" conventions in the codebase and they disagree:

- **UTC** — `new Date().toISOString().slice(0, 10)`, used **63 times** for the
  default transaction date, "is this in the future", month scoping
  (`curMonth()`, `:1147`), the week start, and every `todayISO` check.
- **Local** — `isoDay()` at `:2444-2447`, which correctly uses
  `getFullYear()/getMonth()/getDate()`, and is what the **entire motivation
  engine** runs on: streaks, XP, badges, weekly goals (`:2489`, `:2529`,
  `:2550`, `:2959`, `:3048`, `:29069`).

For a user in Israel (UTC+3), between 00:00 and 03:00 local the two are a day
apart. Concretely:

- Log an expense at 01:00 on the 5th → it is **dated the 4th**, and on the 1st of
  a month it lands in the **previous month's budget**.
- The streak engine says it's the 5th; the transaction says the 4th. So *"I
  logged today and my streak still broke"* — which is a complaint the July study
  already recorded.
- For US users the error inverts: log at 20:00 and the row is dated **tomorrow**,
  where `t.date > today` filters exclude it from the balance entirely.

**Fix:** `isoDay(new Date())` is already the correct helper. Replace the 63 UTC
sites with it and delete the second convention. Mechanical, high value.

### 3.2 There are five money formats, and `Intl.NumberFormat` is used zero times

`Intl.NumberFormat` does not appear anywhere in 29,726 lines. Everything goes
through hand-rolled helpers that disagree with each other:

| Helper | Line | Output for the same number |
|---|---|---|
| `fmtCur` / `dollars` | `:1118` | `₪12,480.50` |
| `compactMoney` | `:8767` | `₪12k` |
| `dollarsWhole` | `:1136` | `₪12,481` |
| `jrCur` | `:4304` | `₪12,481` |
| `invFmt` | `:1618` | `USD 12480.50` for unlisted codes |

`fmtCur` hardcodes `toLocaleString("en-US")` and always **prefixes** the symbol.
Of the 50 currencies in `CURRENCY_OPTIONS` (`:337`), the postfix ones — `zł`,
`kr`, `Kč`, `Ft`, `lei` — come out as `zł1,234.00`, a form no Pole writes. A
Russian user gets `₽1,234.56` instead of `1 234,56 ₽`.

Worse, on the app's most-viewed screen the hero balance says `₪12,480.50` and
the chart directly beneath it labels its zero line **`$0`** — a hardcoded literal
at `:8875` — while its min/max labels say `₪12k`. Two currencies and two
conventions, inches apart.

And `jrCur` / `dollarsWhole` both do `Math.round(Math.abs(n))` with no
caller-side sign, so **a negative net worth renders as a positive number** — a
loss shown as a gain in the onboarding story numbers.

**Fix:** one `Intl.NumberFormat(appLocale, {style:'currency', currency:
SYM_TO_CODE[sym]})` inside `fmtCur`, and delete the other four. Highest-leverage
single change in the whole report.

### 3.3 NaN%, 100%-but-not-done, and -9900%

- **Goal shows 100% while not complete.** `:9361-9362` — `pct` is rounded,
  `done` is not. At 99.6% the row reads **100%** but shows no DONE badge and the
  bar stays orange. That is literally the complaint.
- **A goal with target 0 renders `NaN%`.** `:12319` guards with
  `!form.target` — but `form.target` is a *string*, so `"0"` is truthy and gets
  through. The edit path (`:12333`) correctly checks `n > 0`; create doesn't.
  Result: `"NaN%"` text, `width: NaN%`, and a permanent DONE badge.
- **Six more unguarded percentage denominators**: `:9101`, `:9146`, `:12067`,
  `:15710`, `:15713`, `:11576` — any period with zero spend but a non-empty row
  list prints `NaN%`.
- **Savings rate is unclamped** (`:9191`, `:8387`): ₪100 income against ₪10,000
  spend renders **-9900%** at `fontSize: 26` in a fixed-width card. With no
  income at all it renders a lone `-`, which reads as a broken screen rather than
  "no data".
- **`-₪0.00`**: `:8368` sums raw floats with no `round2`, so a month that nets
  exactly zero after drift prints `-₪0.00` (same at `:10721`, `:16839`).
- **Runway contradicts itself**: `:18504` will happily say `2500.0 mo` of
  breathing room while `:15382` caps the same concept at `12+ mo`.

### 3.4 Dates: five month arrays, four conventions, and Hijri

On top of the UTC/local split in §3.1:

- **Five separate hardcoded English month arrays** (`:2469`, `:7922`, `:8766`,
  `:18110`, `:22872`). So the chart axis and savings projections say "Mar 2027"
  in English while `dateLabel` (`:9420`) *is* localized — two date languages on
  one screen.
- **US month/day order hardcoded** on the chart axis (`:8773`): `5/8` means May 8
  to the code and August 5 to every Israeli, Russian and Arab user.
- **`ar-SA` gives Hijri dates.** `:6546` maps Arabic to `ar-SA`, and
  `toLocaleDateString("ar-SA", …)` defaults to the **Islamic calendar** with
  Eastern-Arabic digits — `١٤ رجب ١٤٤٧` in the Activity list, next to Gregorian
  ISO everywhere else. Should be `ar-u-ca-gregory`. (The same map still carries
  retired `es`/`fr`/`de`/`pt` codes.)
- **Four formatting conventions**: app-locale (`:9427`), *device* locale
  (`:12443`, `:15544`, `:16281`), and bare `toLocaleDateString()` with no options
  (`:21447`, `:21479`, `:26253`, `:26357`). The last group has **no `isNaN`
  guard**, so a malformed timestamp renders the literal text **`Invalid Date`**
  on the stock detail and Bank Sync screens. The other sites *do* guard, which
  shows the omission is accidental.

### 3.5 Richard is told numbers the user can't find on screen

`:14492` bypasses `fmtCur` entirely and rounds: the model receives `₪12480`
where the UI shows `₪12,480.37`. So Richard quotes figures that don't match
anything visible — which reads to a customer as the AI being wrong.

Still open from 17 Aug: C3 (Richard told budgets in dollars), C4 (catch-up
spending all lands on today).

## 4 · "Full RTL support" — what it actually is

The funnel translation on 19 Aug was real work and it helped. Everything past the
funnel is unchanged. Current counts, measured today:

| | count |
|---|---|
| Logical CSS properties (`marginInline`, `textAlign:"start"`…) | **9** |
| Hardcoded `textAlign: "left"` | **69** |
| Hardcoded `textAlign: "right"` | **35** |
| Absolute `left:` positions | **60** |
| `translateX()` slide animations | **36** |
| `row-reverse` handling | **0** |

`applyLangDir` (`:432`) sets `document.documentElement.dir` and that is the
entire RTL mechanism. Inline styles override it. Concretely, in Hebrew today:

- **The very first screen is broken.** `fieldWrap` (`:6319-6329`) pins the input
  icon at `left: 16` with `padding-left: 46px`. In RTL the text right-aligns into
  the 15px side while the icon and its 46px gutter stay on the left — so the
  email and password text collides with one edge and leaves a gap at the other.
- **Every progress bar fills from the wrong end.** `SplitBar` (`:5315`, `:5317`)
  uses `left: 0` and `left: mark%`, both physical. Budget and goal bars grow
  *toward* the start of their label, and the target marker lands mirrored.
- **Grow animations play backwards** — `transformOrigin: "left center"` at
  `:7195`, `:11576`, `:12062`.
- **The back arrow points forward** — `:13215` hard-rotates the chevron 180°.
- **Money strings have no bidi isolation.** Zero `unicodeBidi` or `dir="ltr"`
  wrappers on any amount in the file. `-` and `₪` are bidi-neutral, so inside an
  RTL paragraph `-₪1,234.56` can reorder to `1,234.56₪-` — the minus sign
  appearing to belong to the *next* number. In a finance app that is the worst
  possible bidi bug.
- **`letterSpacing` breaks Arabic.** 429 `letterSpacing` declarations, including
  the core form label every sheet uses (`:5467`). Arabic is cursive — letter
  spacing disconnects the ligatures, so `مبلغ` renders as `م ب ل غ`. It reads as
  a broken font, not a style choice. The 186 `textTransform:"uppercase"` are
  simply no-ops in Hebrew and Arabic, so those eyebrow labels lose their
  hierarchy entirely.
- **The Investing and Business tab bars never translate.** `:28124` reads
  `{t.icon ? t.label : tr(t.id)}` — tabs *with* an icon use the raw English
  label, and every tab in `INVESTING_HUB_TABS` (`:28060`) and the business `TABS`
  (`:18475`) has one. So switching to Hebrew translates the bottom nav on some
  screens and not others.
- **The intro carousel hardcodes `$` in all four languages** — and inconsistently:
  `+$3,000` (en, `:513`), `+3,000$` (he, `:665`), `+3 000$` (ru, `:969`), plus
  raw `$2,840` / `$412` literals at `:6037-6041` that aren't translated at all.
  Three conventions in the user's first sixty seconds, none matching what the app
  then shows them.
- **Half-translated sentences.** `:12049` renders `of ₪5,000 מתוקצב`. `:11813`
  glues English plural rules (`" category"` / `" categories"`, `", exclusive"`)
  onto translated strings — unexpressible in Russian or Arabic. `:12086` passes
  the literal `"Targets"` where the line beside it uses `tr("byCategory")`.
- **English-only placeholders**, one prompting shekel users with a dollar
  example: `placeholder="…Can I afford a $1,500/mo apartment?"` (`:14039`; also
  `:11105`, `:13285`, `:17010`, `:18063`, `:20559`, `:25095`, `:26619`).

And whole screens are still hardcoded English. `PrivacyView` (`:26425-26550`) has
**zero** `tr()` calls — "Name", "Date of birth", "Export my data", "Danger zone",
"Type DELETE to confirm". `ProfileView` (`:27786-27936`) is ~28 `ProfileRow`s,
every label an English literal. Same for `BusinessView`, `StockView`,
`StockScoutView`.

A Hebrew user completes a properly translated onboarding, arrives in the app, and
every screen after that is in English. That's arguably a worse experience than
plain English throughout, because the mixed bidi throws numerals and punctuation
to the wrong end of the line.

## 5 · Why it looks cheap — there's no design system in use

There *is* a design system (`design-system/dist/richy-ds.js`, with tokens). **The
app does not import it.** `grep design-system budget-app.jsx` returns one
comment. What the app has instead:

| | count |
|---|---|
| Inline `style={{…}}` objects | **3,695** |
| `var(--token)` references | 48 |
| Distinct `borderRadius` values | **20** (2,4,5,6,8,9,10,11,12,13,14,16,18,20,999…) |
| `fontSize` declarations | 1,745 across **43 distinct sizes** |

Twenty corner radii and forty-three font sizes is not a style — it's forty-three
separate judgement calls made on forty-three different days. That is the
mechanical reason similar screens don't look like each other, and it's what
"cheap" actually means here: nothing lines up with anything else because there is
no scale to line up to.

`design-system/README.md` is honest about it: *"Only 6 of the app's ~60 UI
functions were extracted."*

**The specific things that read as cheap:**

- **The close button on every sheet is the letter `x`.** `:5451-5455` — a
  lowercase Latin `x` in the UI sans, in a 30px circle, next to an 18px editorial
  serif title. It is the most-tapped control in the app and it's a typed
  character, not `×` and not an icon.
- **No hover states at all.** `:hover` appears **zero times** in the file. Press
  feedback is opt-in: 393 `<button>` elements, **18** with `className="jr-press"`.
  About 370 buttons have no hover, no press, and no focus feedback — the app
  feels dead under the finger.
- **Disabled buttons are unreadable.** `BigBtn` (`:5529`) puts `T.ink3` on a
  10%-black tint — roughly **1.4:1**. The user can't read what they're blocked
  from doing.
- **Long category names don't truncate.** `:12113` has no `whiteSpace` /
  `overflow` / `textOverflow`, so a long name wraps to three lines and shoves the
  whole budget row out of alignment. Same for overlay titles (`:12348`).
- **Nav labels overflow.** `:28126` — `fontSize: 9.5` with `whiteSpace: "nowrap"`
  and no ellipsis, five tabs sharing `calc(100% - 32px)`. On a 320px phone that's
  ~50px per label; Russian `Активность` and Arabic `الميزانيات` simply overflow.
- **Content sits under the notch.** `index.html:5` sets `viewport-fit=cover`, but
  only **6** `env(safe-area-inset-*)` uses exist. Every full-screen journey
  overlay (`:13210`, `:13192`, `:23644`, `:23811`, `:25995`) starts at a fixed
  top padding — back button and progress bar land under the Dynamic Island. The
  toast (`:4981`) is pinned at `bottom: 96` while the nav pill it must clear uses
  `calc(20px + env(safe-area-inset-bottom))` (`:29714`), so it overlaps the tab
  bar on a home-indicator iPhone.
- **Sheet centering depends on an animation.** `:5429` sets `left: "50%"` with no
  `transform: translateX(-50%)`; the centering lives only in the
  `@keyframes sheetSlideUp` fill-mode (`:28963`). If that animation is ever
  suppressed, every bottom sheet sits half off the right edge.
- **z-index collision at 500** — `:22402` (story takeover) and `:26146` (confirm
  dialog) both claim it, with `95/91/90/80/35/30` used elsewhere and no shared
  constant. Stacking is decided by DOM order.
- **Blank grey bars instead of empty states.** `:12060` renders
  `<div style={{width:"100%"}} />` when `segTotal === 0` — a literally empty bar,
  no message. `GradientShimmer` (`:3740`) exists but is wired only to AI thinking
  text, so data-loading surfaces fall back to placeholder text in an empty input
  (`:20677` "Live price loads here").
- **Four native `window.confirm`/`window.alert` dialogs** remain (`:26186`,
  `:26297`, `:26443`, `:26464`). In the Capacitor shell those render as a system
  alert titled with our Vercel origin — on Bank Sync and Delete Account, two of
  the most consequential screens. `Overlay` (`:4691`) is already well built;
  use it.

## 6 · Accessibility

| | count |
|---|---|
| `onClick` handlers | 488 |
| `role="button"` | **0** |
| `tabIndex` | **1** |
| `aria-label` | 33 |

**The secondary text colour fails contrast in both themes — and it's used 661

T.ink3 = dark ? "#6B5C4E" : "#B0A396";

I checked the maths on this one myself. `T.ink3` carries every caption, every
form label (`:5467`), every date, and — worst — the **inactive bottom-nav labels
at 9.5px** (`:28126`). The app's primary navigation is below the legibility floor.
`T.heroMut` (`:50`) adds 102 more failures on the hero card.

**This is a one-hex-value fix that clears 661 failures.** Nothing else in this
report has that ratio.

**No Dynamic Type.** Every size is hardcoded px, so a user who enlarges text in
iOS Settings sees no change at all — and 26% of the app's text is already under
12px. "I can't read the small text" is both an accessibility failure and, I'd
bet, a large share of the "looks cheap" complaints.

**84 inputs, 0 labels.** `htmlFor` appears **0** times; `<label>` appears 3
times; `<input>` appears 84 times. The universal form primitive `FormRow`
(`:5464-5479`) renders its label as an unassociated `<div>`, and its `<select>`
branch (`:5471`) has no accessible name either. So every field in every sheet —
amount, category, target, deadline — is announced to a screen reader as an
unnamed edit box. **One component fixes all 84.**

**Divs used as buttons.** `role="button"` 0, `tabIndex` 1. Confirmed interactive
`<div onClick>`: the Savings Rate and Transactions cards (`:9192`, `:9197`), the
whole Goals section (`:9350`), **every budget row** (`:12109`), and a full-screen
tap layer (`:22402`). Keyboard and switch-control users cannot reach any of them.

**Icon-only buttons with no name.** `JrIconBtn` (`:4576-4585`) — the back button
in every onboarding, trip and business journey — has no `aria-label` and no
`title`. 33 `aria-label`s exist against 393 buttons; zero `SVGIcon` lines carry
one.

**Focus rings are removed from exactly the elements that need them.** `:3496`
correctly defines a global `*:focus-visible` outline — and then **67 inline
`outline: "none"`** declarations override it on the inputs (`:4894`, `:5476`,
`:5471`, `:6329`, `:5790`…). Inline beats stylesheet, so every text input loses
its focus ring. `.jr-field` (`:4289`) at least substitutes a border and shadow;
the ~80 fields that don't use it substitute nothing.

**Touch targets under 44pt** (Apple HIG and WCAG 2.5.5 both require 44):
`JrIconBtn` 34×34 (`:4580`), sheet close 30×30 (`:5451`), `SegRow` pills ~30px
tall (`:5504`), plus ~25 more.

**Modals**: Escape is handled globally (`:29451`) — good. But `role="dialog"`
appears once, and `Overlay` (`:5421`) portals to `document.body` with no focus
containment or restore, so tabbing out of an open sheet lands invisibly on the
page behind it.

Reduced motion, to be fair, is handled properly (`:2763`, `:2799`, `:2976`).

## Smaller things I noticed, for whoever picks this up

- **CSV import has no `reader.onerror`** (`:9968`). An unreadable file — an
  iCloud placeholder, a permissions error — produces no feedback at all; the
  paste box just stays empty.
- **Invites can be permanently invisible.** `CLOUD.findInvites` (`:3244`) is
  called with a bare `.catch(function(){})` at `:28629`. `firestore.rules:48`
  reads `request.auth.token.email`, which is stale after `CLOUD.updateEmail`
  (`:3206`) until the token refreshes — so the query is denied and swallowed. The
  partner insists they sent an invite; the user sees nothing.
- **Sync-inbox drain has no `.catch`** (`:28903`). A rejected save is an
  unhandled rejection, the inbox docs are never deleted, and `syncSeenRef`
  (`:28873`) stops them being reprocessed. The transaction shows on screen but was
  never persisted — and the inbox eventually 429s with `inbox_full`.
- **`skipWaiting()` sits outside `waitUntil`** (`sw.js:48`), so it runs before
  the precache resolves, and `activate` then sweeps old caches and claims live
  pages — a page running the previous deploy can be claimed by a SW whose cache
  no longer holds its assets.
- **`res.status()` with a possibly-undefined code** (`api/stock.js:259`) throws a
  `RangeError` into the catch at `:427`, which calls `sendErr` again on a response
  that may already have sent headers → the function crashes and the client gets
  an HTML 500.
- **Stock Scout re-fires on every tab visit.** `genRef` (`:22562`) is a
  per-instance `useRef`, so the "once per day" guard at `:22560` only holds once a
  result is saved — meanwhile each visit can trigger a fresh Opus call and ~70s of
  uncancellable spinner. (Moot if we turn the feature off, but relevant if it
  comes back.)
- **`sendVerificationEmail` (`:5852`)** is a bare `fetch` to EmailJS with no
  timeout and no `.catch`, and has **zero call sites**. Dead code that will bite
  whoever wires it up.
- **`fmtCur` renders `Infinity`** as `$∞` (`:1118`) — `Math.abs(n || 0)` catches
  `NaN` because it's falsy, but not `Infinity`. Every division reaching it is
  currently guarded, so this is latent, not live.
