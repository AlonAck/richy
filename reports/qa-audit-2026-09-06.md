# Richy — QA sweep and remediation plan, 6 September 2026

## Context

Two months of customer complaints cluster into four shapes: **screens that get
stuck**, **dead ends where money goes in and cannot come out**, **numbers shown in
the wrong place**, and **screens that look cheap**. Legal and accessibility are in
scope too.

Five audits already exist (17 Aug, 25 Aug, 30 Aug, 2 Sep, 5 Sep). So this sweep
does three jobs rather than repeating them:

1. **Re-verify** whether yesterday's criticals were fixed.
2. **Sweep new ground** — the onboarding funnel, the Richard chat flow, every
   money-in/money-out pair, currency formatting, and the native iOS app. The
   5 Sep report names most of these as "still not swept".
3. **Answer the manager's real question**, which is not "what else is broken"
   but "why do the same complaints keep arriving after five audits".

**Deploy state.** `HEAD` was `a7be44b` when this sweep started and is `f0871d9` now
— another session was fixing while I audited, and `budget-app.jsx` grew from 36,072
to 36,153 lines mid-sweep. **Every finding below was re-verified by code string
against `f0871d9`**, so grep the quoted code rather than trusting a line number.
The 1,629-line "Business Account v2" diff is still uncommitted.

**Clock.** App Store submission is **23 September** — 17 days.

### The new findings, in the order I would act on them

**1. Richard fakes an answer every time the network or the quota fails — and it
is live.** When a chat request errors, the handler throws the error away and
substitutes a 250-line keyword bot as though it were Richard:
`var response = err || !text ? Richard(msg) : text;` (`:19412`). Offline, rate
limited, session expired, conversation too long, upstream timeout — all five
produce a confident, generic paragraph that ignores the user's numbers. The server
writes a good, actionable message for every one of those cases and **the user never
sees any of them.** Forty-seven lines earlier, in the same function, the Focus Mode
branch handles this correctly. **This is the most likely single cause of the
"Richard just gives generic advice" complaints**, and Richard is the whole
differentiator. Details and fix in §6.1.

**2. Two badge families can never fire for anyone.** `cushionMonths` is computed
from two `onboardingData` keys that **nothing in the codebase ever writes**, and
`d.cleared` is read but never written. Between them, seven achievements and both
the Wall Builder and Debt Breaker ranks are unreachable by any user, ever (§1.3,
§6.5.4, §6.6). Three lines of code.

**3. The App Store listing sells six features the shipping binary does not have.**
On 4 September the plan switched from a Capacitor wrap of the web app to a native
SwiftUI app in `RichyIOS/` (`NATIVE_BUILD.md:1`). That app is **6,538 lines against
the web app's 36,072** — roughly 18% of the product. `APP_STORE_LISTING.md`
promises savings accounts, a debt payoff tracker, trip planning, IOU notes with
reminders, household sharing and CSV import. **None of them exist in `RichyIOS/`.**
Its own README says so plainly. That is Guideline 2.3.1 (Accurate Metadata) — and
if it clears review, it is a launch week of 1★ "the features aren't in the app"
reviews, which are close to permanent.

**4. A user who signs up on the phone never gets a plan, and there is no way to
get one.** `RichyIOS/README.md` states that an account created on the phone gets
the onboarding questionnaire and Richard's first plan "the first time it opens the
web". The native app has no browser hand-off and no questionnaire. Richard's plan
is the single thing the product is positioned on. This is the purest dead end in
the codebase: the user is told they have a money coach, and the coach has nothing
to work from, permanently.

**5. Closing the tab loses your last transaction — and the crash screen tells you
it didn't.** Saves are debounced 800 ms (`:34964`). There is **no `beforeunload`
and no `pagehide` handler anywhere** in 36,072 lines. Add a transaction and swipe
the PWA away inside that window and the write never happens. The crash screen
(`:4027`) says *"Your data is safe in the cloud"* — which is false in exactly the
case where a user reads it. This is the same defect as B1 (Sign Out) with a
different trigger, and it is the most plausible mechanical explanation for
"my transaction disappeared" complaints.

**6. The contrast work landed, but two palettes were never measured — and one of
them is the hero card.** `b551786` fixed `T.ink3` and the roadmap records the
result correctly. I recomputed it independently and it holds:

| Token | Ratio | Verdict |
|---|---|---|
| `T.ink3` `#7A6B5C` on `T.bg` `#F7F3EE` | **4.65:1** | passes AA |
| `T.ink3` on `T.card` `#FFFFFF` | **5.14:1** | passes AA |
| `heroFaint` on the default blue hero | **1.95:1** | fails badly |
| `heroMut` on the purple hero | **2.82:1** | fails |

So `T.ink3` is **done** — and two things follow. First, `ROADMAP.md:522` still
describes the `ink3` contrast failure as one of "two known, still-open defects",
which is stale, and the "781 `T.ink3` uses" figure keeps being reported as a defect
counter when it is now just a usage count. Second, and this is the real point:
**`heroMut` (70 uses) and `heroFaint` (29 uses) were never measured at all**, and
they sit on the hero card — the most-looked-at surface in the app. Sub-labels at
~2:1 are unreadable in sunlight, and it is a direct cause of "looks cheap": the hero
reads washed-out and unfinished. Same story for `JOURNEY_DARK.ink3` (§5.2).
**Roughly a six-value fix.**

**7. Reminders only fire while the app is open.** `fireDue` (`:35196`) runs off an
in-page timer. `sw.js:142` has a `push` listener, but **`pushManager` appears
nowhere in the codebase** — nothing ever subscribes, and no server sends. So a
reminder set for Tuesday arrives whenever you next happen to open Richy. The store
description sells "Notes for who owes you and who you owe, **with reminders**".
The native path (`LocalNotifications`) is a **Capacitor** plugin — and Capacitor is
no longer the ship route, so on the SwiftUI binary that call can never resolve.

**8. Every money figure in the app is formatted `en-US`, in all four languages.**
`fmtCur` (`:1449`) ends in `abs.toLocaleString("en-US", …)` and always *prefixes*
the symbol. A Russian user sees `1,234.56` where their locale writes `1 234,56`.
One function, one line.

**9. "Full Hebrew and Arabic support" is an overclaim, and it is in the promotional
text.** `document.documentElement.dir` does flip to `rtl` for he/ar (`:674`) — but
the app contains **107 hardcoded `textAlign: "left"/"right"` and 40 physical
`marginLeft`/`paddingLeft` values against only 4 logical (`marginInlineStart`)
properties**. Physical values do not flip under `dir=rtl`. So the block direction
mirrors and the contents do not: a half-flipped layout, which reads worse than not
flipping at all. `isRTL()` is used exactly once in 36,072 lines — to rotate a
chevron. `index.html:2` is also hardcoded `lang="en"` and never updated, so a
screen reader reads Hebrew text in an English voice.

### Two smaller things that are cheap and visible

- **Three different chrome colours, none of them the app's.** `index.html:8`
  declares `theme-color: #8970C6` (purple). `manifest.webmanifest:9` declares
  `theme_color: #141210` (near-black). The default in-app theme is **blue**
  (`applyTheme("blue")`, `:239`). The phone's status bar therefore never matches

- **The crash screen is a third design system.** It hardcodes gold `#C8973A`
  instead of the theme accent, is English-only in a four-language app, and its
  only button re-runs the crash.

## 1. The onboarding funnel — never swept before, and it holds the worst bug in the app

### 1.1 CRITICAL — "Redo Questionnaire" is a one-tap trap that locks you out of your own app, and then deletes your budgets

This is the single clearest match to the complaints being escalated. It is a chain
of four separate defects that compound:

**Step 1 — one tap, no confirmation.** The Plan screen renders
`onClick={props.onRetake}` with no dialog.

**Step 2 — the flag is written to the server immediately.**
```js
function handleRetakePlan() {          // :35829
  setOnboardingDone(false);
  merged.onboardingDone = false;
  persistBlob(merged);                 // straight to Firestore
}
```

**Step 3 — the app is replaced, and there is no way out.** The render gate is
`if (!onboardingDone) return <OnboardingScreen … />` (`:35821`) — and it is passed
**no `oData` prop**, so all ten screens come up blank rather than pre-filled. There
is no X, no Cancel, no back-to-app control anywhere in `OnboardingScreen`. Hardware
and browser Back are explicitly swallowed:
```js
if (!onboardingDone || !catchUpDone) return true;   // :35747 "mid-setup - swallow, never lose progress"
```
Force-quitting does not help — `onboardingDone: false` is already on the server, so
the trap survives a reinstall. The user must complete 10 screens, sit through a
multi-beat animated "math story" whose beats are gated behind animation timers, and
wait out plan generation, just to get back to their own data.

**Step 4 — finishing it silently destroys their budgets.**
```js
if (suggestedBudgets && suggestedBudgets.length) {
  setBudgets(suggestedBudgets);
  merged.budgets = suggestedBudgets;     // :35582 — assigned, not merged
}
```
The button says *"Yes, set them up"* under *"Richard suggests these monthly
limits"*. Nothing says **replace**. Every custom limit, every folder budget, gone.
The savings block **four lines below it is correctly guarded**
(`if (savAmt > 0 && !(savings && savings.length))`) — so the author knew the guard
was needed and it was omitted here.

**Fix:** confirm sheet on the button; pass `oData` and prefill; add an `onCancel`
that restores `onboardingDone = true`; don't persist the flag until the retake
completes; guard the budgets assignment the way the savings one already is.

### 1.2 CRITICAL — tapping "Save" on your own financial details deletes what makes Richard personal

`EditFinancialView.handleSave` (`:32273`) builds a fresh object from nine fields:
```js
props.onSave({ lifeStage, income, essentials, savings, debt, goalName, goalAmt, timeline, age });
```
and `onSaveFinancial` (`:35358`) writes it as a **whole-object replace**:
`save({ onboardingData: oData })`.

Dropped every time: `coreProblem`, `moneyLeaks`, `overspendEst`, `prefLang`,
`prefCurrency`, `prefPeriodMode`, `prefPeriodStart`, `prefPeriodEnd`.

`coreProblem` — the answer to "what is your primary financial challenge", screen
4 of 10 — is written in exactly **one** place (`:8403`) and read in **seven**,
including Richard's main chat system prompt (`:19345`), the Full Analysis prompt
(`:18800`), the decision helper (`:17223`) and the plan generator (`:8414`).

So: open Profile → financial details → change nothing → tap **Save**, and your AI
money coach quietly stops knowing what you came to it for, in every conversation,
forever. Nothing tells the user. And per 1.1, the only way to set it again is the
trap.

*Richard is the thing the product is positioned on. This is a Save button that
turns him generic.*

**Fix:** `props.onSave(Object.assign({}, oData, { lifeStage, income, … }))` — one
line. Then add `coreProblem` to `EditFinancialView` as an editable chip row.

### 1.3 HIGH — four badges and a whole rank are permanently unearnable, because of two key names

```js
var target     = Number((data.onboardingData || {}).savingsTargetPct || 0);   // :3282
var essentials = Number((data.onboardingData || {}).monthlyEssentials || 0);  // :3296
var cushionMonths = essentials > 0 ? savTotal / essentials : 0;              // :3297
```
`grep -n 'monthlyEssentials\|savingsTargetPct'` returns **exactly those two lines
in 36,072**. Nothing ever writes either key — onboarding writes `essentials`
(`:8403`), and no savings-target percentage is collected at all.

So `cushionMonths` is **`0` for every user who has ever used Richy**, which
permanently locks:

- `g-06` "Soft Landing", `g-07` "Sleeping Soundly", `g-08` "Nothing Can Touch Me",
  `g-09` "Fort Knox" (`:3230`–`:3233`)
- the **Wall Builder** rank at level 21 (`:2966`) and half of **Debt Breaker** at
  level 31 (`:2968`)

Users grind past level 21 and the title never arrives. And because `targetPct` is
always 0, the "green month" streak the entire Profile screen is built around
silently means *"didn't go negative"* rather than *"hit my savings target"*.

`MOTIVATION_SYSTEM.md` is 32,000 words. Part of what it describes cannot happen.
**Fix: rename two reads.**

### 1.4 HIGH — a savings goal silently destroys money paid in above target

```js
saved: Math.min(g.target, g.saved + n)     // :15643
```
Target $1,000, saved $900, you add $500 → saved becomes $1,000. **$400 is gone**,
with no warning and no toast, and the sheet just closes. The *remove* path four
lines up correctly routes through a confirm (`setConfirmAmt(n)`). Add is
unguarded. Same asymmetry as 1.1 step 4.

## 3. Numbers in the wrong place — eleven formatters that disagree

There are **eleven** money formatters in this file. Two of them (`dollarsWhole`,
`jrCur`) are byte-identical duplicates. The consequences:

### 3.1 CRITICAL — Richard is told a loss is a gain, four lines under a comment promising he can't be

`fmtCur`'s own doc comment (`:1457`) states the rule:

> …an unsigned amount silently reads a loss as a profit and an overdraft as
> savings. **Every money value in an AI prompt goes through here** [`dollarsSigned`].

The Full Analysis chat snapshot breaks it (`:21214`):
```js
// Grounded in the very figures on screen, so an answer can never quietly
// disagree with the card the user is looking at while they read it.
var snapshot = … + ", kept " + dollars(net) + " (savings rate " + savRate + "%), net worth " + dollars(netWorth)
```
`dollars` is **unsigned**. Income 3,000 against spend 4,000 produces the literal
prompt `kept $1,000.00 (savings rate -33%)` — a sentence that contradicts itself,
sent to the model as ground truth. A user in net debt is told their net worth is
positive. **Five comparable prompt builders elsewhere (`:22482`, `:22598`,
`:22690`, `:22691`, `:23987`) all use `dollarsSigned` correctly.** This one site is
the outlier. Two words.

### 3.2 HIGH — "Left to spend" renders overspend with no minus sign

`:10878` and `:16734`: colour is the *only* indicator that the number is negative.
Overspend a trip by 120 and the card reads **"LEFT TO SPEND — $120"**. Colour-blind
users, screenshots and screen readers all get "one hundred twenty dollars left to
spend" while the user is 120 over. The correct pattern already exists at `:33274`.

### 3.3 HIGH — every currency is formatted `en-US`, and the symbol is always a prefix

`Intl.NumberFormat` appears **zero times** in 36,072 lines. All seven formatters end
in `toLocaleString("en-US")`. The app ships 50 currencies and 4 languages, so:
Russian RUB renders `₽1,234.56` instead of `1 234,56 ₽`; Polish, Swedish, Czech,
Hungarian, Romanian, Danish, Norwegian, Icelandic and the Euro are all **suffix**
currencies rendered as prefixes. This is the complaint's own words — numbers in the
wrong place.

The store listing claims "**50 currencies with correct symbols and decimal rules**".
Several symbols are invented for uniqueness (`Col$`, `Mex$`, `Nkr`, `CN¥` — the code
comment admits it), and `COP`, `HUF`, `IDR` are declared 0-decimal where ISO 4217
says 2. "Correct" is not supportable.

### 3.4 The rest

- **Three hardcoded `$` that ignore the selected currency.** `:26267` labels a TASE
  stock's market cap in dollars while every other stat in the same array uses
  `invFmt`; `:25977` feeds `$` into Richard's stock-explainer prompt for an
  Israeli security; `:18636` mixes `$` and `₪` inside one sentence of car advice.
- **Fixed-width money cells overflow.** `width: 64` + `flexShrink: 0` + no
  `overflow` at `:29832`/`:29839`. Business revenue over ~99,999 paints over the
  progress bar beside it.
- **Neither `k`-abbreviator has a millions tier.** A ₪2,500,000 portfolio axis reads
  **`₪2500k`**.

### 3.5 Two things I expected to find broken and did not

- **`toFixed` is never used for money arithmetic.** All 62 uses are SVG paths,
  animation delays and chart dash arrays. Rounding goes through `round2()`
  (228 sites) with `Number.EPSILON`. Correct.
- **No path renders `NaN`, `Infinity` or `undefined` as text.** Every denominator I
  traced is either `|| 1`-guarded or gated behind a `> 0` filter. `InfoRow` even
  falls back to `"--"`. This is careful work.

## 5. Accessibility — the honest numbers

The counter that has been tracked across four audits (`aria-label` vs button count)
is not measuring the right thing, and two of the three real problems have never been
named.

**What is actually true:**

| | |
|---|---|
| `onClick` handlers | **552** |
| `aria-label` | **54** |
| `tabIndex` | **1** |
| `role="button"` | **1** |
| `aria-modal` | **1** |
| `inert` | **0** |

Most of the 443 buttons carry visible text, which is a valid accessible name — so
the raw 10:1 ratio overstates it. The measured problems are:

- **74 buttons contain only an `SVGIcon` and have neither `aria-label` nor
  `title`.** Verified examples: delete a trip budget category (`:16606`), delete a
  logged trip expense (`:16863`), dismiss a Richard banner (`:33693`), and **two
  adjacent unlabelled chevrons** on the business P&L month stepper (`:29822`) that
  VoiceOver announces as "button, button".
- **23 `<div onClick>` handlers a keyboard cannot reach at all** — including two
  destructive ones: remove a dashboard widget (`:9764`) and permanently dismiss a
  Richard tip (`:10090`). Both carry `title` (a mouse tooltip) and nothing else.

### 5.1 HIGH — the app has 49 modal sheets and none of them manage focus

`Overlay` (`:6436`, **49 usages** — Add Transaction, Add Budget, every bottom sheet)
portals to `document.body` and renders a fixed full-screen div with **no
`role="dialog"`, no `aria-modal`, no `.focus()` on open, no saved/restored
`activeElement`, no Escape handler, and no `inert` on the page behind it.**

This is the *inverse* of a focus trap, which is worse than none: a keyboard user
opens the Add-Transaction sheet, presses Tab, and lands on the dashboard **behind**
the sheet — still focusable, visually obscured. A screen reader reads the whole page
underneath as though the sheet were not there. On close, focus is on `<body>`, so
the next Tab restarts from the top of the app. Combined with `closeTopLayer`
registering only 3 of 11 overlays, modals are the single weakest surface in the app.

### 5.2 Contrast — the tracked metric is wrong, and the real failure is elsewhere

I computed the ratios independently and they agree with the palette's own comment:

## 6. The Richard chat, and money in with no way out

This is the section that matters most, because it is where the two headline
complaints actually live. Both sweeps here landed after the rest of the report was
drafted; everything below is re-verified against `f0871d9`.

### 6.1 CRITICAL — every chat failure is disguised as a real Richard answer. Live.

```js
function(err, text) {
  setChatLoading(false);
  var response = err || !text ? Richard(msg) : text;    // :19412
```

`Richard()` (`:18473`) is a ~250-line **keyword-matching canned-response engine** —
`if (has("compound interest", "compounding"))` returns a stock paragraph about
Einstein. The `err` object is discarded: never read, never logged, never shown.

So every failure mode collapses into a plausible-looking fake reply:

| What happened | What the server actually sent | What the user sees |
|---|---|---|
| Offline / captive portal | fetch reject | a confident canned paragraph |
| Rate limited (30 req / 5 min) | 429 "Richard needs a short breather — try again in a few minutes." | a confident canned paragraph |
| Session expired | 401 "Your session expired. Sign in again." | a confident canned paragraph |
| Conversation too long | 413 "That conversation is too long…" | a confident canned paragraph |
| Upstream timeout | 504 "Richard took too long to answer." | a confident canned paragraph |

**Every one of those server messages is well written, actionable, and unreachable.**

The proof it is unintended is 47 lines earlier in the same function. The Focus Mode
branch does exactly the right thing (`:19365`):
```js
setChat(function(p) { return p.concat([{ role: "assistant",
  text: "I hit a snag thinking that through - give it another try in a moment. (" + err.message + ")" }]); });
```

**This is almost certainly the single largest driver of the "Richard just gives
generic advice" complaints.** A user with no signal, or one who has hit the quota,
gets textbook filler that ignores their numbers — and reads it as "this AI is
useless", not "I am offline". Richard is the entire differentiator; this makes him
look stupid on every bad network.

**Fix:** delete the `Richard()` fallback from the error path and mirror Focus Mode —
append an error bubble carrying `err.message` (the server already writes
user-facing copy) plus a Retry that re-sends the message.

### 6.2 HIGH — a hard 20-turn wall, hit silently. Live.

`sendChat` sends the **entire** thread uncapped (`nc.map(apiMsg)`, `:19294`). The
server rejects `messages.length > 40` with a 413 (`api/chat.js:130`). Forty messages
is **twenty user turns**. Turn 21 onward always 413s — and lands in 6.1's silent
fallback.

So after a long, genuinely good conversation, Richard permanently degrades into a
keyword bot mid-chat and never recovers. The only cure is "New chat", and nothing
tells the user that. Same wall by size: `downscaleImage` allows ~46,000 chars per
image and **re-sends every image on every turn** against a 100,000-char budget
shared with a ~15k system prompt — so **two attached images permanently kill the
thread.**

**Fix:** send a sliding window (`nc.slice(-30)`), strip `att.b64` from all but the
most recent user message, and — once 6.1 is fixed — surface the 413 with a "Start a
new chat" action.

### 6.3 MEDIUM-HIGH — there is no way to stop a response, and the whole header locks

An `AbortController` **already exists** inside `callClaude` (`:17069`) but is only
ever fired by the internal timer; nothing in the UI can reach it. The send button
becomes a non-interactive spinner, and History and New-chat are disabled too
(`:20075`, `:20104`) — so a user who realises mid-question that they asked the wrong
thing is locked out of every control for up to **55 seconds, or 90 in Focus Mode**.

**Fix:** hand the existing `ctrl` out through an `abortRef`, swap the spinner for a
stop square, and stop disabling New chat. The `.catch` already routes an
`AbortError` into `finish()`, so this is 90% plumbed.

### 6.4 MEDIUM — the Advisor error banner is dead code, and a failure shows a green dot

`setErrMsg` is called **exactly once in the whole file, with `""`** — so the banner
at `:20103` can never render. `getAdvice()` has the same disease as 6.1: on error it
silently substitutes `localAnalysis()`. The status line then reports success with a
**green dot** and "Analyzed your month — just now", over a locally-computed heuristic
presented as Richard's analysis.

### 6.5 Money in, money out — the full matrix

**Five areas are clean, and they are the model to copy:**

| Area | Adds | Removes | Reachable? |
|---|---|---|---|
| Savings pots | `deposit` `:23530` | `deleteEntry` `:23594` — pushes an offsetting `transferTx` when `fromMain` | yes |
| Investing | `:24589`, `savePlanBuy` | `deleteActivity` `:24610` | yes, via "See all" |
| Trips | `logExpense`, reserve | `deleteEntry`, `undoReserve`, `removeTrip` (cleans `reserveTxId`) | yes |
| Budgets | caps only — no money committed | filter-out | yes |
| Business expenses | `logExpense` `:28260` | `deleteExpense` `:28267` | yes |

**Four fail, and three of them are live:**

**6.5.1 CRITICAL (uncommitted) — "Pay from pot" moves no cash and reports the
balance in the wrong direction.** `moveTaxPot` writes only to `biz.taxPot.entries`
and never touches `biz.entries`, the actual cash ledger. Then:
```js
function bizTaxReserved(biz) { … e.kind === "release" ? -(e.amount || 0) : (e.amount || 0) … }  // :22355
function bizSpendableCash(biz) { return round2(businessCash(biz) - bizTaxReserved(biz)); }      // :22361
```
A release **reduces** `bizTaxReserved` while `businessCash` is unchanged — so
**spendable cash goes UP by exactly the amount the owner just paid the tax
authority.** It is not a no-op; it moves the headline number backwards. A business
owner pays £3,000 to HMRC, records it, and Richy tells them they now have £3,000
*more* to spend. Confirmed absent from `HEAD` — this is fix-before-you-commit, not
live. Two siblings on the same screen: **pot-history rows have no delete control at
all**, so a mistyped "Set aside £50,000" can only be masked by a release (which then
inflates spendable cash); and `deleteCapEntry` removes a paid-invoice revenue row
without removing that invoice's auto-generated `taxPot` entry, stranding a
permanently un-deletable reserve.

**6.5.2 HIGH (live) — the business capital-history delete is correct and unreachable
past six rows.** `deleteCapEntry` is complete — it even pushes an offsetting
`transferTx` when `entry.fromMain` — and it is bound to a trash button. But
`capHistory` is `.slice(0, 6)` (`:29192`) with **no "See all" expander**; the only
`"See all"` string in 36,153 lines is the Investing one. Mistype £10,000 of revenue,
log six more entries, and both the error and the phantom £2,500 tax bill it created
are permanently un-deletable through the UI. *This is exactly the bug class from
yesterday's report — a working safety mechanism that nothing renders.*

**6.5.3 HIGH (live) — Richard confirms a goal contribution, then silently does
nothing.** `case "goalAdd":` (`:17452`) validates only the amount and the name
length. Its neighbours in the same switch all check reality — `savingsMove` calls
`hasSavings`, `noteSettle` calls `hasOpenNote`, `budget` calls `hasCat`/`hasFolder`.
There is **no `hasGoal` helper at all**, even though the caller passes `goals` into
`validationCtx` (`:19353`) — where it is **never read**. Two silent failures follow:
a name that does not match maps the array to itself; and for a *linked* goal it
writes `g.saved`, which `goalSavedAmount` never reads for linked types. The manual
UI knows this and hides its own sheet behind `if (!isLinked)` — Richard's path has
no such guard. The user says "put £200 into my house fund", sees a confirmation
card, taps Apply, gets a warm confirmation, and the goal does not move.
**A confirmed-then-vanished commitment is the most trust-destroying shape this can
take.**

**6.5.4 HIGH (live) — a paid-off debt cannot be set to zero, and the badge for it
can never fire.** The guard `!(parseFloat(form.balance) > 0)` (`:22834`, `:23007`)
is right for creating a debt and wrong for editing one, and `DebtView` has **no
payment ledger at all** — the only mutators are `saveForm` and `doDelete`. So the
only way to represent "I paid this off" is **Delete**, which erases the history.
And `grep "cleared:"` returns **nothing** — `d.cleared` is read at `:3360` and
written nowhere, so `i-04 Cleared the Slate`, `i-05 Free and Clear`,
`i-07 Snowball's Chance` and the **Debt Breaker** rank are permanently unachievable.
The user makes the final payment on a credit card — the best moment in the entire
product — and the Save button is dead, the only option is Delete, and no achievement
fires.

**6.5.5 MEDIUM (live) — settling an IOU is one-way.** `doSettle` (`:14312`) deletes
the note and creates a transaction; deleting that transaction does not restore the
note, and no inverse of `settleNoteToTx` exists. Settle the wrong IOU and you retype
it from memory. The undo pattern already exists in this file
(`goalActionUndoCard`, `:12843`).

### 6.6 Two badge families, seven achievements, zero users

Combining 6.5.4 with §1.3: **`cushionMonths` is always 0** (two key names nothing
writes) and **`d.cleared` is never written**. Between them, `g-06`, `g-07`, `g-08`,
`g-09`, `i-04`, `i-05`, `i-07` and **both the Wall Builder and Debt Breaker ranks**
are unreachable by any user, ever. The retention layer that `MOTIVATION_SYSTEM.md`
describes in 32,000 words has a hole in it that three lines of code would close.

### 6.7 Verified clean, and worth saying

`callClaude` has a real 55 s deadline with a `done` latch and `clearTimeout` on every
path — **there is no unsettled-promise path**, so the "0 `.finally()`" figure is not
biting here. `setChatLoading(false)` is the *first* statement in both response
callbacks, so the spinner always clears. There is **no `dangerouslySetInnerHTML` and
no `innerHTML =` anywhere in the file** — model output is never rendered as HTML, so
**no XSS**. And chat history is capped (`CHAT_ARCHIVE_MAX = 20`, `CHAT_MSGS_MAX = 40`,
`CHAT_TEXT_MAX = 4000`), so Firestore document growth is handled.

## 7. What I think the right move is

### 7.1 The decision that has to be made first is not a bug — it is which binary ships

The 5 Sep plan is a good plan and I would not rewrite it. But it was written for the
**web app**, and on 4 September the thing being submitted to Apple became a
**different codebase**. Sorting its 17-day list by which product each item reaches:

| | Reaches the App Store binary? |
|---|---|
| privacy.html, terms.html, listing copy, `api/delete-account.js`, the `api/` guardrails, `firestore.rules`, EmailJS | **yes** — shared backend and legal |
| A1 hero, D1 titles, C3 modals, the onboarding trap, `coreProblem`, `cushionMonths`, the 11 formatters, `Overlay` focus, RTL, contrast, font sizes | **no** — those screens do not exist in `RichyIOS/` |
| the entire `RichyIOS/` surface | **only place it matters — and no audit has ever looked at it** |

So roughly 80% of the current remediation list improves the product for **today's
live web users** — which is real and worth doing, they are the ones complaining —
but buys **nothing** toward 23 September. Meanwhile the code that will actually be
reviewed has never been audited by any of the six sweeps.

**The scope arithmetic does not work.** ROADMAP is at *Phase 2 of 8*. `RichyIOS/` is
6,538 lines against the web app's 36,153 — about 18%. The commitment recorded on
5 September is **"ship everything": full parity, nothing deferred**. Building the
remaining ~17 feature areas *and* clearing Tier 0 *and* getting a Mac session, a
plist, TestFlight and review in 17 days is not a schedule, it is a hope.

**Three honest options. This is Alon's call, not mine — but I would not let the date
make it by default:**

1. **Slip to Monday 2 November.** `CAMPAIGN_LAUNCH_2026-10.md` already names it as
   the next-best date and already has a hard go/no-go gate written for 20 September
   (risk R1: *"If it slips, slip the launch"*). Six extra weeks clears Tier 0, gets
   honest parity, and gets telemetry in before real users arrive. **This is what I
   would recommend.**
2. **Ship native v1 at reduced scope on 23 Sep and rewrite the listing to match
   exactly what is in the binary.** Viable, but it means publicly dropping six
   advertised features, and it ships an unaudited codebase.
3. **Revert to the Capacitor wrap for v1.** `capacitor.config.json` and
   `native/PrivacyInfo.xcprivacy` are still committed and `NATIVE_BUILD.md`
   documents the whole flow. It would hit the date with every advertised feature
   present — but it ships every open Tier 0 defect in this report straight to the
   App Store, which is the worst possible content for launch-week reviews.

**Whichever is chosen, the listing has to stop describing a product that isn't in
the box.** That is Guideline 2.3.1 and it is the most likely rejection here.

**And Business Account v2 does not get committed until §6.5.1 is fixed.** The diff is
good work, but as it stands "Pay from pot" tells a business owner they have more
cash after paying their tax bill than before. That is not a bug to ship and fix
later.

### 7.2 Do these regardless of the date, because they are false statements

Cheap, and each one is currently untrue in a document users and Apple can read:

1. `api/delete-account.js` — erase `whatsappOptIn/{uid}` and `whatsappPhones/{phone}`.
   One function. A live privacy-policy sentence is false until it lands.
2. `privacy.html` — add the phone number to §1, add **Meta** and **EmailJS** to the
   §3 processor table, and correct the "display preferences never leave your device"
   line (§4.3), which the code contradicts three times.
3. `APP_STORE_LISTING.md` — fill in the demo credentials (still literally
   `[FILL IN before submitting]`, the most common 2.1 rejection for a Finance app),
   add the four missing data categories, and correct the "clearly fictional" claim
   about the Leumi demo merchants.
4. Strip the ranking instruction and `confidence` field from the Stock Scout prompt,
   and delete `localStockScout`'s pick generation. Yesterday's lesson holds: **put
   the guardrail where financial strings are rendered, not at the API boundary** —
   it has now escaped three times.

### 7.3 Then, for the web app that has live users today

In this order. Everything here is small.

**First — Richard, because he is the product and he is currently lying.** Delete the
`Richard()` fallback from the chat error path and mirror what Focus Mode already
does 47 lines above it (§6.1). Add the sliding window so turn 21 stops 413-ing
(§6.2). Together these are perhaps thirty lines and they are the highest-leverage

**Second — the six one-or-two-line fixes that are each doing real damage:**

| Fix | Change |
|---|---|
| `dollarsSigned(net)` and `dollarsSigned(netWorth)` at the Full Analysis snapshot | stops telling Richard a loss is a gain (§3.1) |

### 7.4 The process problem, which is the actual answer to "why does this keep happening"

Six audits in three weeks. Two fixes shipped today; the rest of the list is three
weeks old. Counters keep moving the wrong way *while* audits are being written. The
reason is not carelessness — the code is thoughtful, the comments are genuinely
excellent, and several things I went looking for turned out to be correctly built
(`round2`, the division guards, `focus-visible`, the disclaimers, the network
timeouts, account deletion, zero dead toggles across 540 state pairs). The reason is
that **nothing except a human reading 36,000 lines ever tells anyone something
broke**:

- **no tests** — no runner, no `test` script, no `*.test.*` file;
- **no web CI** — `.github/workflows/` contains exactly one job, and it compiles
  *iOS*. Nothing lints or type-checks the web app;
- **no error telemetry** — `sentry|analytics|posthog|mixpanel|gtag` returns **0**
  across the whole repo;
- **nobody has ever run either app and clicked through it.** Every one of the six
  audits, including this one, is static analysis. The 5 Sep report says so; so does
  the `RichyIOS/` README ("what CI cannot do is run the app").

Three things would change that, in this order:

1. **Error telemetry — under a day.** With a reporter live on 30 August, the
   `watchBrief` title would have been a ticket within an hour of the first tap
   instead of surviving three audits.
2. **A browser pass, this week.** Start the local harness, walk the funnel, the
   retake trap, the hero at each timeframe, and the 49 sheets with a keyboard. Half
   a day would have caught §1.1 and §5.1 without reading a line of code. **I did not
   do this today because the session is read-only** — it is the single highest-value
   next step and it needs no new tooling.
3. **A gate, five checks, failing the build.** Every value `currentTab` can take
   resolves to a real dictionary key; no new `toISOString()` date site; no bare
   `dollars(` inside a string sent to the model; no new `<div onClick>`; no ticker
   symbol or `confidence` field in a render path.

And one observation worth more than the gate: **the Swift code already does the
thing the web code never does.** `RichardChatViewModel` uses
`defer { isReplying = false }` — the exact guarantee the web app is missing in all
36,153 lines (`.finally(` = 0). The pattern to copy is already in this repo.

### 7.5 The one thing I would push back on

The roadmap's own callout says two audits in a row asked to freeze features, and the
commit between them was a 3,900-line feature. Since then the pattern has repeated at
larger scale: the 5 Sep list went out, and the next day's work was **the native
app**, not the list. I am not arguing the native app is wrong — it is the right
architecture. I am saying that the Tier 0 list has now lost to something more
interesting **four times**, and no amount of audit writing fixes that. Either it
gets one owner and a date, or the seventh audit will open the same way this one did.
